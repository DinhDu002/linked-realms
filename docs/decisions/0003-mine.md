# 0003 — Mine

Status: accepted, 2026-10-29

## Context

Phase 1B adds `GoldToken`, `GoldMine`, `packages/miner` and mining in the Map server. PLAN.md section 5.2 and decisions D8 and D9 fix the puzzle, the Round time, the Retarget rule and the issuance. They left open the exact `submit` interface, how the next Challenge is derived, what happens at the supply cap, how the Map server reaches the miner, and the Initial Target, which PLAN.md says to measure in this step.

## Decisions

1. **`submit(round, nonce, rewardWallet)` names the Round.** A Solution for an old Round reverts early with `StaleRound(submitted, current)`, so a miner can tell "lost the race" from "invalid Solution" and stops wasting fees on retries.
2. **At most one win per block** (`RoundAlreadyWonInThisBlock`). Without it, a miner holding several Solutions could chain Rounds inside one block, because each next Challenge would be predictable from the transactions before it. A miner's `eth_call` runs against the latest block, which right after a win is the block where the new Round started, so it reverts with this error although the Solution is good for the next block. The miner then sends the transaction anyway, with a fixed gas limit; it can only land in a later block.
3. **Next Challenge** = `keccak256(abi.encode(previousChallenge, rewardWallet, nonce, blockhash(block.number - 1), block.prevrandao, block.timestamp))`. Block data makes the next Challenge unknown until the winning transaction is mined. The first Challenge mixes the chain id and the `GoldMine` address, so two deployments never share Challenges.
4. **Retarget arithmetic.** Every `retargetIntervalRounds` wins: `target = target * clamp(actual, expected / 4, expected * 4) / expected`, computed with `mulDiv`, saturating at `2^256 - 1` and never below 1. `GoldMine.nextTarget` and `nextTarget` in `packages/shared` are cross-checked with generated vectors (P8).
5. **Supply cap.** `GoldToken` is `ERC20Capped` at 21 million and mints only for the minter set once with `setMinter` (`GoldMine`). When a reward would cross the cap, it is cut to what remains; after that, Rounds go on with no reward, so the Retarget clock keeps working.
6. **Mining params are fixed at `initialize`** (P4); only an upgrade can change them. On anvil only, `Deploy.s.sol` reads `DEV_ROUND_SECONDS`, `DEV_RETARGET_INTERVAL_ROUNDS` and `DEV_INITIAL_TARGET`, so Retargets can be watched in minutes. On Base Sepolia the rules from `packages/shared` are used as they are.
7. **The miner polls `currentRound()`** every second instead of following `RoundStarted` logs. One `eth_call` per second is cheap, and polling cannot miss a Round the way an expired log filter on a public RPC can. Up to one second of work per Round can be wasted; at 60-second Rounds that is under 2%.
8. **The Miner lives as long as the Map server process**, not the room: mining goes on when nobody is on the Land, and whoever joins sees its status. Mining is off at every start (P5); only the Land owner's session can switch it on, and it uses 1 thread unless the owner picks more, up to `MINING_MAX_THREADS` (default: all cores but one).
9. **The Mining key** is a fresh key created by the Map server in a local file (mode 0600, default `packages/map-server/.data/mining-key`). It only pays fees; the reward wallet is always the Land owner's, read from the chain (P2). On anvil the Map server funds it itself; elsewhere the Land owner funds it from a faucet.
10. **Initial Target** = `2^256 / (REFERENCE_HASH_RATE * 60)` with `REFERENCE_HASH_RATE = 3,200,000` hashes per second: one `miner` thread on the reference machine (the project owner's Apple M5, Node 26, `hash-wasm` keccak256) finds one Solution per 60 seconds on average. `pnpm --filter @linked-realms/miner bench` measured 3,186,725 (5 s run) and 3,272,673 (20 s run) hashes per second for one thread, and 3.11 million per thread with two threads; the reference rate rounds that down. The value lives in `packages/shared/src/rules/mining.ts` and reaches `Rules.sol` through code generation. A wrong guess here costs little: the first Retarget corrects it by up to 4×.

## Consequences

- A Land owner whose Mining key runs out of test ETH stops winning Rounds until they fund it again; the Map server warns at start-up.
- Changing the Initial Target, the Round time or the Retarget rule needs a new deployment or an upgrade, and a regenerated `Rules.sol`.
- The simulation in `contracts/test/GoldMine.simulation.t.sol` runs in every `forge test`, so a change that breaks convergence fails CI.
