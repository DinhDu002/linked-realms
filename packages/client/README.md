# @linked-realms/client

The reference Land UI: Phaser 4 + Vite. A Land's Map server serves the built `dist/` from the Land's own origin, and the Shell loads it inside its frame. It shows the Land's map and every Character on it, and walks the Player's Character with the arrow keys or WASD. On a touch screen (CSS `pointer: coarse`) it also shows a pad in the lower left: hold a finger on it and slide the way to walk, in 8 directions (`padKeys` in `src/input.ts`).

```bash
pnpm --filter @linked-realms/client dev   # http://localhost:5181, /play proxied to ws://127.0.0.1:2567
pnpm --filter @linked-realms/client test
pnpm --filter @linked-realms/client build
```

- **Shell** (`shell.ts`, `docs/protocols/shell-land-ui.md`): accepts the Shell's `linked-realms/connect` message (only from `window.parent`, api 1, first one only), keeps its port, receives `init` (Land, Character, handoff), sends `travel` when the Character steps onto a Gate, and shows `travelRefused` in plain words. `signMessage` asks the Shell to sign a line of text in its own prompt and settles with the `signResult` of its id: the signed Land message, or an error the page explains in plain words. Opened outside a frame, the page says "Open this Land from the Shell" and does nothing else. This page never asks for a password or 24 words, and holds no key.
- **Connection** (`connection.ts`): one WebSocket to `/play` on the page's own origin (wss on https), binary Protocol Buffers (`@linked-realms/shared/land-protocol`). The first message is `hello` with the handoff; `mine_switch` carries the Land owner's signed switch. An `error` from the Map server is shown in plain words and the socket then closes. The page connects once the WebAssembly module of `@linked-realms/core` has loaded, which formats Gold and checks the switch line.
- **Scene** (`scene.ts`): takes decoded `ServerMessage`s (`welcome`, `joined`, `left`, `moved`, `notice`, `mine_state`, `mine_won`) and sends `input` (dx, dy, growing seq) when the keys change. Each Character is labelled with its name (or its short address), `[AI]` when it is driven by an AI, and a star for the Land's owner.
- **The Mine** (`mine.ts`, `docs/protocols/map-server-node.md`): the HUD always shows the Mine's line from the last `MineState` ("Mine ON · 2 threads · fast · 1.2 kH/s · rewards to Mai · 3 Blocks won"). While it is on or starting, the Mine on the map pulses, its gear spins faster with more threads and sparks rise faster with more hashes (dimmer and slower while starting). On `MineWon` everyone sees a ring, a burst and "+N GOLD" rising, where N is the reward the Map server reports, and a HUD line. With `prefers-reduced-motion`, only the texts. A visitor cannot verify any of it (P1).
- **The Land owner's switch:** only the Land owner sees "Switch the Mine" (or taps the Mine), chooses on or off and the threads (1 to the Node's `maxThreads`), and signs the switch line (`buildMineSwitch`) in the Shell's prompt. The page sends it as `mine_switch` and shows the Map server's `MineSwitchResult` in plain words. The control is disabled while the Mine is `unavailable` and while a switch is being signed.
- Map servers are untrusted (P1) and maps are data (P6): the map text goes through `parseLandMap`, Characters through `readCharacter`, the Mine's state and wins through `readMineState` and `readMineWon`, and the ground and Mine are drawn from textures generated in code. Nothing is loaded from a URL the server provides.
- Pure modules (`connection`, `gate`, `input`, `interpolate`, `mine`, `players`, `shell`, `tiles`) have Vitest tests; `scene.ts` and `main.ts` are thin Phaser/DOM glue. The client does no movement prediction, so it ignores the `seq` in `moved`.
